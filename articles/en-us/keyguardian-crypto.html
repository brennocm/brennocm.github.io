KeyGuardian: fixing the crypto in my own password vault

Nov 24, 2026

KeyGuardian is a Flutter password manager I built in college. The user signs in with Firebase and sets a master key only they know, and passwords go to Firestore encrypted on the device. The promise was that the backend would only ever hold ciphertext.

Rereading the code, I found that the first version only partly kept that promise. The master key became the AES key with almost no processing, nothing protected the integrity of stored values, and anyone who could read the database could test master keys offline at the cost of one AES operation per guess. This post covers what was wrong, the new scheme and how existing vaults were migrated. The whole change is one commit.

Concepts

KDF (key derivation function)

A password typed by a person has little entropy and can't be used directly as a cipher key. A password KDF such as PBKDF2, scrypt or Argon2id turns the password into a key of the right size and is deliberately slow (the last two also use memory). The user pays that cost once per unlock, and whoever is guessing pays it once per guess. A random per-user salt keeps the same work from being reused against several accounts.

Authenticated encryption (AEAD)

AES-CBC only provides confidentiality. If someone changes the ciphertext, decryption returns a different plaintext, or garbage, and reports nothing. An AEAD such as AES-GCM also produces an authentication tag: any bit changed in the ciphertext, the nonce or the associated data makes decryption fail. The associated data (AAD) isn't encrypted but is covered by the tag, which lets you bind a value to the context it was written in.


The original design

All the crypto lived in an EncryptionService built on the encrypt package. The key came from here: 

enc.Key _prepareKey(String masterKey) {
  String keyString = masterKey.padRight(32, '0').substring(0, 32);
  return enc.Key.fromUtf8(keyString);
}

The master key was padded with the character '0' to 32 characters, cut at 32 and used as an AES-256 key in CBC mode, with a random IV per value. The stored format was iv:ciphertext in base64. To check whether the master key was right, the app stored the fixed string MASTER_KEY_VERIFICATION_2024 in users/{uid}, encrypted with that same key, and on unlock checked whether it decrypted back to the same string.


What was wrong

Cheap guesses

The most serious problem is the missing KDF. The verification value is a known plaintext (it's in the source code) encrypted under a key that is the master key itself. Anyone who can read the users/{uid} document, through a misconfigured Firestore rule, a leaked admin credential or access to the Firebase project, can test master keys offline. Each guess costs a zero-padding step and a two-block AES decryption, so a laptop tests millions per second and an ordinary master key falls quickly.

Predictable key

Padding with '0' means a 10-character master key yields a key in which 22 of the 32 bytes are known. Cutting at 32 characters also drops everything after that, so a long passphrase loses some of its strength. This matters less than the missing KDF, since the search space is still the master key's, but it doesn't help.

No integrity

CBC without a MAC is malleable. Flipping a bit in the IV flips the same bit in the first block of the decrypted plaintext, so someone with write access to the database can change the first 16 bytes of a stored password in a controlled way without knowing the key, as long as they know or can guess the contents. Since every value used the same key and nothing tied a value to where it was stored, you could also copy the ciphertext of one credential into another, or from one field to another, and the app would decrypt it normally.


The new scheme

 master key
      │  PBKDF2-HMAC-SHA256, 600,000 iterations,
      │  16-byte salt per user
      ▼
 vault key (32 bytes, memory only)
      │  AES-256-GCM per value: random 96-bit nonce,
      │  128-bit tag, AAD = keyguardian:v2:<uid>:<field>
      ▼
 Firestore: v2:<nonce b64>:<ciphertext+tag b64>

Derivation

The master key goes through PBKDF2-HMAC-SHA256 with 600,000 iterations, the value the OWASP Password Storage Cheat Sheet recommends for this algorithm, and a random 16-byte salt per user. The salt, the iteration count and the algorithm name are stored in users/{uid}.kdf. The master key is never stored or sent, and the derived key only exists in memory, in a VaultKey object whose toString() prints <redacted> so it can't end up in a log by accident.

Argon2id holds up better against GPUs and would be the ideal choice. I stayed with PBKDF2 because it has public test vectors (RFC 7914) and a mature pure-Dart implementation with no native dependency. Since the algorithm and parameters are now stored with the vault, moving to Argon2id in a future version is a migration like the one described below.

The app refuses parameters below 600,000 iterations or an unknown algorithm. A tampered document already wouldn't open the vault, because the verification would fail, but the rule keeps a bug or a future version from silently accepting a lower cost.

Encryption

Each value is encrypted with AES-256-GCM, a random 96-bit nonce and a 128-bit tag. With random nonces, NIST's limit is 232 values per key, far above what a personal vault holds. The AAD is keyguardian:v2:<uid>:<field>, so a value copied into another account or another field fails the tag check. The master key verification uses the same mechanism, and a wrong key now fails the tag check instead of returning garbage.


Performance

The first test with pointycastle's PBKDF2 took about 6.8 s for 600,000 iterations on my desktop, which is too long for an unlock screen. The generic implementation reprocesses the HMAC key and allocates buffers on every call. In PBKDF2 with HMAC-SHA256 the HMAC key is always the same password, so the SHA-256 states after processing ipad and opad can be computed once. Each iteration then costs exactly two SHA-256 compressions, and the time dropped to about 0.8 s on the same machine.

Rewriting a crypto primitive is the kind of thing I'd block in a code review if it came without tests. The new implementation is checked against both RFC 7914 vectors (1 and 80,000 iterations) and compared with pointycastle on random passwords and salts, with lengths chosen to hit the SHA-256 padding edges and the rule for passwords longer than one block. Derivation runs in a separate isolate with compute() so the UI doesn't freeze.


Migrating existing vaults

Existing users had passwords in the old format, and nobody should lose data or have to do anything. On unlock, the app reads users/{uid}. If there's no kdf field, the vault is from the old version: the master key is checked with the old scheme and, if it's correct, the app reads every credential, decrypts it with the old scheme, encrypts it again with the new one and writes everything, together with the KDF parameters and the new verification value, in a single Firestore batch.

The batch is atomic. If the write fails halfway, nothing changes, and the migration runs again on the next unlock. Values already in the v2 format are skipped, and an old value that doesn't decrypt is left as is. Firestore accepts at most 500 writes per batch and one goes to the user document, so the migration handles vaults of up to 499 credentials. Above that, the app reports it and doesn't migrate halfway.


Tests

The crypto core is in lib/core/crypto/vault_crypto.dart, with no Flutter dependency, and has 15 tests:

  1. the RFC 7914 vectors and the comparison with pointycastle described above;
  2. round trips with an empty value and non-ASCII characters, and a different nonce for every value;
  3. rejection of a wrong key, of one changed byte in the ciphertext and of a value moved to another user or field;
  4. rejection of malformed input and of downgraded KDF parameters;
  5. decryption of a value produced by the old version of the app, so the migration can read what exists today.

Limitations

The master key can't be recovered: forgetting it means losing the vault. Firestore security rules live in the Firebase console, outside the repository, and each user should only read and write users/{their uid}/**. The tests cover the crypto, but the migration hasn't yet been exercised against a real Firebase project. The 0.8 s was measured on a desktop; on a mid-range phone unlocking will take longer, and I haven't measured it yet.

One older bug is still there: a credential that fails to decrypt shows up as ******, and editing and saving it writes the asterisks over the real password. None of this protects against a compromised device, where whoever controls the system can read the master key as it's typed.


Final thoughts

KeyGuardian's mistake is common in apps that encrypt on the client: the cipher was there, but the key came straight from a password and nothing checked integrity. When I review an app like this now, I start with three questions: where does the key come from, what happens if someone changes a ciphertext, and how much does a guess cost for someone holding a copy of the database. For the first version of KeyGuardian the answers were "from a password with zeros at the end", "nothing" and "almost nothing".
