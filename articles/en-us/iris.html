Iris: an Android self-protection SDK that decides nothing

Dec 1, 2026

In the UnCrackable post, every protection fell to one hook: root detection, anti-debugging, Frida detection. Each one ended in a boolean inside the app, and whoever controls the device controls that boolean. I came out of it with a question: what would a detection library look like if it were written with that in mind from the start?

Iris is my answer. It's an Android SDK in Kotlin and C that looks for root, Frida, Xposed, debuggers and repackaged APKs, and makes no decision at all. It returns a report signed with an Android Keystore key, and a reference server in Go verifies the signature and decides whether to allow, review or deny. The name comes from Greek myth: Iris is the messenger of the gods, who carries the message and judges no one.

I tested it on an Android 14 emulator, clean, rooted and with Frida injected, but not yet on a range of real devices. Don't use it in production yet.

Concepts

RASP

Runtime application self-protection is code that runs inside the app and tries to notice when the environment has been compromised: root, instrumentation, a debugger, a modified binary. OWASP MASVS groups these controls under RESILIENCE. The weakness is well known: the detection code runs in the same process the attacker controls.

Key attestation

When an app creates an Android Keystore key with a challenge, the device's secure hardware (TEE or StrongBox) issues a certificate chain that ends at a Google root. The key's certificate carries an extension with the challenge, the package and signing certificate of the app that asked for the key, and the bootloader state. Those fields are written by the hardware, outside the app's process, so a hook in the app can't change them.

Play Integrity

Google's API that returns a verdict about the app and the device, signed by Google and checked on the server. It takes a requestHash field, which binds the verdict to one specific request.


Why the SDK doesn't decide

Iris has no isSafe(), doesn't block screens and doesn't close the app. Each check becomes a signal with a fixed code (ROOT-001, HOOK-001, DEBUG-001, TAMPER-001) and the evidence behind it, and the report goes to the backend. If the app decided on its own, one hook on that decision would switch everything off. On the server, the decision is out of reach for whoever holds the device.

The other rule is that a check that couldn't run is reported as unavailable, never as clean. If someone blocks reads of /proc/self/maps, the report says it couldn't look, and the server sends it to review instead of allowing it. 

{"schema":1,
 "signals":[{"id":"HOOK-001","probe":"maps",
             "evidence":"/memfd:frida-agent-64.so (deleted)"}],
 "unavailable":[{"probe":"tracer",
                 "reason":"could not read /proc/self/status"}]}

Reading /proc without going through libc

The cheapest bypass I saw in the crackmes was hooking libc: make open fail for /proc/self/maps, or make strstr never find "frida". So the native part of Iris doesn't call libc to read files. On arm64 and x86_64, openat, read, close, faccessat and getdents64 are issued with the syscall instruction written inline (svc #0 and syscall), and string matching happens in Kotlin. In the release AAR, the 64-bit libraries import no libc file functions. The 32-bit ABIs fall back to libc's syscall() wrapper, which can be hooked.

The checks in version 0.1:

  1. ROOT-001: su and Magisk binaries at known paths;
  2. ROOT-002: a system image signed with test-keys;
  3. ROOT-003: Magisk mounts in /proc/self/mounts;
  4. HOOK-001: Frida, Xposed, LSPosed and Substrate libraries in /proc/self/maps;
  5. HOOK-002: Frida agent threads in /proc/self/task/*/comm;
  6. DEBUG-001 to 003: TracerPid, a debuggable build and a connected Java debugger;
  7. TAMPER-001: an APK signing certificate other than the expected one.

The signed report

A report on its own is just JSON. A clean report captured on another device can be replayed, one can be built by a script, or it can be edited in transit. To close that, the full flow is: 

 server   POST /v1/challenge
          32 bytes, single use, valid 2 minutes
     │
     ▼
 app      iris.inspectAndSign(context, challenge)
          checks → JSON report
          new P-256 key in the TEE, attested
          with the challenge
          signs the report, deletes the key
     │
     ▼
 server   POST /v1/verify
          chain to Google's root, revocation
          challenge, package, signer, boot
          signature over the report
          signals → allow, review or deny

The key is new for every challenge and deleted right after, so no long-lived key sits on the device for someone to reuse. When the Keystore fails, which happens on old devices or broken implementations, the message goes out unsigned with the reason in attestation_error, and the server treats it as a missing check.

The attestation proves that the message was created after the challenge, that the key lives in secure hardware, which package and signing certificate asked for the key, and whether the bootloader is locked. A repackaged APK shows up here even if someone switched off TAMPER-001 in the app. What it doesn't prove is that the report is honest: whoever controls the process can call the same Keystore API and sign a clean report. That's why the server weighs the attested fields more heavily than the signals.


The verifier

The repository's server/ is a Go service that uses only the standard library. It issues challenges and, for each message, checks the chain to Google's roots (by the root's public key), the revocation list, the challenge, the attestation security level, the package, the app's certificate, the ECDSA signature over the report and the boot state. The default policy:

deny: an invalid chain or one outside Google's roots, a revoked certificate, an unknown or reused challenge, software attestation, the wrong package or signer, a signature that doesn't verify, any HOOK or TAMPER signal.

review: ROOT or DEBUG signals, unavailable checks, a message without attestation, an unlocked bootloader or unverified boot.

allow: none of the above.

The app can sign anything with its own attested key, including a certificate. An attacker creates a genuinely attested key and uses it to sign a fake certificate with an extension that says "bootloader locked" and whatever challenge they want. That chain verifies signature by signature up to Google's root. What breaks it is requiring the attestation extension to appear only on the first certificate: in the attack, the genuine certificate moves to second place and also carries the extension. A test builds exactly this chain, and it fails if the rule is removed.

Play Integrity sits behind an interface. Checking the verdict is done (package, requestHash equal to the report's SHA-256, token age, app recognition and device integrity), but the binary doesn't make the authenticated call to Google yet.


Testing on the emulator

I used an Android 14 emulator with the google_apis x86_64 image, a userdebug build: it accepts adb root and ships /system/xbin/su. A sample app asks the server for a challenge, runs inspectAndSign and sends the message to /v1/verify.

Clean app

The report came back without signals. With only Google's roots, the server denied it: the emulator's chain ends at "Droid Unregistered Device CA", a Google test root. Trusting that root and allowing software attestation (two options that exist only for testing and log a warning), the answer was review, because the emulator has no hardware root of trust.

Root

This one surprised me. The report still had no signals, with su right there in the system. SELinux denies apps the search of /system/xbin, so faccessat returns EACCES both for su and for a name that doesn't exist. Until then Iris treated EACCES as "can't tell", which was right by accident. Now it checks a control name in the same directory: if the control returns ENOENT, the directory is searchable and the EACCES came from the file itself, which exists. On the emulator the answer is still "can't tell", with no false positive. adb root doesn't give the app anything either; it only restarts adbd as root. What gives this device away is the attestation.

Frida

I injected Frida 17.27.5 with frida-inject into the running app, with a script that does what bypass scripts usually do: hook libc's openat, read and strstr to strip "frida" from /proc/self/maps and make any search for "frida" fail. Then I ran the inspection again in the same process: 

HOOK-001 (maps): /memfd:frida-agent-64.so (deleted)
HOOK-002 (threads): gmain
HOOK-002 (threads): gdbus
HOOK-002 (threads): gum-js-loop
→ deny

The hooks were active, but Iris's reads don't go through libc, and both signals fired. A script that intercepts the syscall instruction or patches libiris.so would get past it. That limit is in the project's threat model.

The same three device tests run in CI on an emulator on every push.


What the review found

Before opening the repository, I reviewed the code for bugs, and four of them went against the project's own rule that a blinded check must leave a trace:

  1. if libiris.so was missing or failed to load, inspect() threw and crashed the app using the SDK. The native checks are now reported as unavailable;
  2. /proc files larger than 4 MiB were cut off silently. An attacker who mapped thousands of regions could push the Frida agent past the cut. A truncated read with no signals is now unavailable;
  3. the thread list stopped at 2048 without saying so. It now grows, and above 65536 threads the check is unavailable;
  4. inspectAndSign handled only some Keystore exceptions, and load() can throw IOException. Any failure now produces an unattested message, and a device that returns only the key's own certificate (no attestation support) is reported as such.

On the server, a String() could panic on an out-of-range value, and every challenge request scanned the whole map while holding the lock. Both are fixed, with tests.


Hands-on

git clone https://github.com/brennocm/iris.git && cd iris
mise install
mise run check          # Kotlin, C, lint and Go tests

# server, pointed at the sample app
cd server
IRIS_PACKAGE_NAME=io.github.brennocm.iris.sample \
  go run ./cmd/iris-verifier

In the app, the integration takes a few lines: 

val iris = Iris(IrisConfig(signingCertSha256 = setOf("AB:CD:…")))

// off the main thread
val challenge = api.getChallenge()
val message = iris.inspectAndSign(context, challenge)
api.verify(message.toJson(), playIntegrityToken)

The step-by-step for the emulator scenarios, with the Frida script, is in docs/scenarios.md.


Limitations

Anything that runs on the device can be forged by whoever controls the process, and Iris doesn't change that: hooking the SDK's Kotlin methods or patching libiris.so gets past the checks. Name matching catches default setups and misses a renamed Frida. Magisk with DenyList hides its mounts. A rooted device with a locked bootloader, or a leaked attestation keybox, passes attestation; the revocation list and Play Integrity narrow that risk without removing it.

The server's challenge store lives in memory and only works with one instance. It still needs testing on real devices (a locked phone, one with Magisk, one with LSPosed) and the Play Integrity call wired in.


Final thoughts

After breaking the UnCrackable apps, I expected to spend most of the time on detection techniques. They turned out to be the smaller part. What took the most thought was deciding what to do with each result, keeping "I couldn't look" apart from "I looked and it's clean", and writing down what attestation proves and what it doesn't. The most serious bugs I found were exactly the places where the SDK went blind without saying so.
