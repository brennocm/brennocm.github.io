blindsight: offline verification of Safe transactions

Oct 10, 2026

On February 21, 2025, Bybit lost about US$ 1.5 billion, the largest theft in the history of cryptocurrency. The multisig wallet contract worked as designed and no private key leaked. The three signers each approved, on their own hardware wallet, a different transaction from the one the web interface showed. The device displayed only a 32-byte hash, and none of them had a way to know that hash belonged to another transaction.

I wrote blindsight, an open source tool in Rust, to do that check. It recomputes offline the hashes the hardware wallet shows, decodes what is about to be signed and warns when the transaction can take over the wallet.

Concepts

Safe and multisig signatures

Safe (formerly Gnosis Safe) is the most widely used multisig wallet contract on Ethereum. It has a set of owners and a threshold: in a 3-of-5 Safe, every transaction needs three signatures. What each owner signs is a hash of the transaction, computed with the EIP-712 standard from fields such as to, value, data, operation and nonce.

The three EIP-712 hashes

EIP-712 splits what gets signed into two parts. The domain hash says where the signature is valid: the Safe's address and, since version 1.3.0, the chain ID. The message hash summarizes the transaction fields. Together they form the safeTxHash, which is the value actually signed. Ledger devices show the domain hash and the message hash; when the signature uses eth_sign, the device can only show the safeTxHash, with no context at all.

Blind signing

Signing a hash without being able to check what it stands for is called blind signing. The signer trusts the web interface that built the transaction to tell the truth about what it does. If that interface, or the machine it runs on, is compromised, the signature goes to a different transaction. The hash on the device is the only piece of data that does not pass through the interface, and it is only useful if someone recomputes it on their own.

CALL and DELEGATECALL

Every Safe transaction has an operation field. With 0 (CALL), the Safe calls another contract normally. With 1 (DELEGATECALL), the target contract's code runs against the Safe's own storage and can rewrite the owners, the threshold, the modules and the implementation pointer kept in slot 0. After that, the attacker needs no further signatures. DELEGATECALL has legitimate uses (the official MultiSend contract batches calls this way), but with an unknown target it is the most dangerous operation a multisig can sign.


The incidents

Bybit, February 2025

According to Sygnia's investigation, the signers were served malicious JavaScript from the S3 bucket behind the Safe{Wallet} interface. The code activated only for specific addresses, swapped the transaction content for hardcoded parameters and was removed about two minutes after execution. The FBI attributed the attack to North Korea.

On-chain, the signed transaction made a DELEGATECALL to an attacker contract, calling a function whose selector matches transfer(address,uint256). To anyone looking, it was a token transfer. The code replaced the Safe's implementation, and the attacker drained the wallet right after. All three owners signed with eth_sign, so the devices showed only the safeTxHash.

WazirX, July 2024

Seven months earlier, WazirX lost about US$ 230 million the same way: a Safe 1.3.0 with threshold 4, three eth_sign signatures, a DELEGATECALL to an unknown contract and slot 0 changed from the official implementation to the attacker's address. WazirX and its custodian disagree about the root cause, but the signed transaction is on-chain and nobody disputes it.

Both transactions are part of blindsight's regression tests, with the hashes recomputed independently from an archive node and from the Safe Transaction Service.


Threat model

blindsight assumes that the machine and the interface that prepared the transaction may be compromised. So it runs somewhere else, with no network, and recomputes everything from the raw parameters. That assumption led to three design decisions:

  1. There is no network code. Networking and async crates are banned from the dependency tree with cargo deny, and in CI the test suite runs inside a network namespace with no interfaces. There is no online mode for anyone to turn on by mistake.
  2. No data comes from a service. Other tools query the Safe Transaction Service to fetch the transaction or the decoded names; blindsight uses only what the user provides and decodes everything locally.
  3. Hostile input does not crash the program. unsafe is forbidden, parsers and decoders are fuzzed, and errors are sanitized before they reach the screen, so malicious data cannot inject control sequences into the terminal.

Two EIP-712 implementations

On every run, the domain hash, the message hash and the safeTxHash are computed twice: by an EIP-712 encoder I wrote by hand and by the one in the alloy library. If the results differ, no hash is printed, because a wrong hash shown with confidence would lead the signer to approve the wrong transaction. Both implementations are tested against 30 real transactions from 8 chains and 5 Safe versions. Each of those transactions was confirmed by the Transaction Service, by an on-chain event or signature recovery, and by an independent Python implementation.

Verified and inferred names

The calldata becomes a tree: multiSend batches and execTransaction calls to other Safes are decoded recursively. Every function name gets a label. It is verified when the target is known to be a contract that implements that function with the right operation; otherwise it is inferred from the selector. A selector is just 4 bytes of the hash of the function signature, and any contract can have a function with the same selector that does something else. The Bybit payload decodes as transfer and comes out marked unverified.

20 detectors

Detectors run on every node of the tree, so putting a payload inside a batch does not hide it. Each detector has a stable ID and a severity that depends on context. The main ones:

  1. BS-DELEGATE-001 / 002: DELEGATECALL to an untrusted contract, or inside a batch.
  2. BS-SEMANTICS-001: the function name is a guess. It becomes critical when it appears together with DELEGATECALL.
  3. BS-OWNERS-001 / BS-THRESHOLD-001: changes to the owner set or the threshold, critical if the new threshold is 1.
  4. BS-MODULE-001, BS-GUARD-001, BS-FALLBACK-001, BS-IMPL-001: enabling modules or replacing the guard, the fallback handler or the Safe's implementation. Any of them lets someone bypass future signatures.
  5. BS-APPROVAL-001 / 002: unlimited approvals, NFT operators and Permit2 allowances.
  6. BS-REFUND-001: gas refunds paid by the Safe. These fields can drain the wallet, and almost nobody reads them.
  7. BS-POISON-001: an address that looks like one in your address book (address poisoning).
  8. BS-REPLAY-001: Safes older than 1.3.0 have no chain ID in the domain, so the signature is valid on any chain.

Each detector has a documentation page, also available with blindsight detectors explain <ID>.


Hands-on

Release binaries for Linux, macOS and Windows ship with checksums, an SBOM and GitHub provenance attestations. The tool has to run on a trusted machine, so verify the download before using it: 

gh attestation verify blindsight-x86_64-unknown-linux-gnu.tar.xz --repo brennocm/blindsight
sha256sum -c blindsight-x86_64-unknown-linux-gnu.tar.xz.sha256

You can also build it from source (Rust 1.90 or later): 

cargo install --locked blindsight

Input can come in three forms. The first is the parameters the Safe interface shows: 

blindsight verify --chain-id 1 --safe 0xYourSafe --safe-version 1.4.1 \
  --to 0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48 \
  --data 0xa9059cbb000000000000000000000000... --nonce 42 \
  --expect-safe-tx-hash 0x...      # the hash your wallet shows

The other two are a Safe Transaction Service JSON or the calldata of an already executed transaction, copied from a block explorer: 

blindsight verify --tx tx.json --chain-id 1 --safe-version 1.4.1
blindsight verify --exec-calldata 0x6a761202… --chain-id 1 \
  --safe 0xYourSafe --safe-version 1.1.1 --nonce 71

With an address book, addresses show up with names, and addresses that look like one in the book are flagged: 

blindsight verify --tx tx.json --chain-id 1 --safe-version 1.4.1 \
  --address-book book.json --current-nonce 42
# book.json: { "Treasury": "0x…", "Ops multisig": "0x…" }

The safeTxHash above is the same one that appeared on the signers' devices. If any of them had pasted the parameters they received into blindsight, on a separate machine, they would have seen the hash match the device and, above it, two critical findings: a DELEGATECALL to an unknown contract and a zero-value "transfer" whose name is only a guess.

Hashes are printed with the labels and letter case each device uses (Ledger shows upper case). Exit codes are there for automation: 0 when there are no findings above --fail-on (default high), 1 when there are, 2 for an input error and 3 when the expected hash does not match. With --format json, the report comes out in a versioned format for other programs to read.


Recommended workflow

  1. Get the transaction parameters from the interface and the hash your wallet shows.
  2. Run blindsight on a different machine from the one that prepared the transaction, ideally offline, typing or copying the parameters.
  3. Pass the on-screen hash with --expect-safe-tx-hash (or --expect-domain-hash / --expect-message-hash). If it does not match, the exit code is 3 and a red line appears at the top.
  4. Read the verdict and every finding. Do not sign if there is a critical or high finding you cannot explain.
  5. Simulate the transaction as well (Tenderly, Foundry), because blindsight executes nothing.

A matching hash proves you are about to sign the same transaction you gave blindsight. The findings are what tell you what that transaction does.


Comparison with other tools

Other projects solve the same problem and are still worth using. The Bash safe-tx-hashes-util is the community reference and the one Safe's own help center points to. safe-hash brought the idea to Rust, and op-txverify, in Go, was the first to do the air-gapped workflow with QR codes.

blindsight differs from them in a few places: the binary has no network code (cargo deny and a CI job with no network enforce this), decoding is local and never uses a service's labels, unverified names are marked, address poisoning is detected and output is sanitized. On the other hand, it does not handle off-chain messages yet, which the other tools support.


Limitations

blindsight does not simulate the transaction or read chain state, so it cannot see balances, current owners or what unknown code does. It tells you a name is a guess and a target is unverified, but it cannot tell you the code is malicious. The embedded registry ages: new chains, new versions of helper contracts and new tokens show up as unknown until the next update. Only the Safe versions from 1.0.0 to 1.5.0 that were officially deployed are supported.

And the tool only helps if someone compares its hash with the device's, character by character.


Final thoughts

Bybit and WazirX add up to about US$ 1.7 billion lost through transactions their own owners signed. The hardware wallet protected the key but showed only a hash, and none of the signers had another source to check that hash against.

blindsight lets the signer redo that computation on an isolated machine, without relying on any service that might have been compromised along with the interface. It does not replace simulation or reading the code, but in both cases it would have shown a DELEGATECALL to an unknown contract before the first signature.
