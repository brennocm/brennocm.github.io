OWASP UnCrackable: reversing levels 1 to 3 on Android

Nov 24, 2026

The UnCrackable apps are the official crackmes of the OWASP MASTG, the mobile application security testing guide. Each app asks for a secret and shows "Success!" when it's right, and every level adds a protection: root detection in Java in the first, the check moved to native code with anti-debugging in the second, and integrity checks, Frida detection and a secret built by obfuscated code in the third.

I solved all three with static analysis: jadx for the bytecode, objdump for the native libraries and, in level 3, Unicorn to run only the function that builds the secret, without running the app. For each level I also give the dynamic route with Frida, for anyone with a rooted emulator, and the MASVS control the protection is trying to meet. The last section covers what this means for whoever writes the defenses.

The APKs come from the MASTG repository. To check you have the same build:

Concepts

APK, DEX and jadx

An APK is a zip holding the manifest, the resources, the app bytecode (classes.dex) and, when there is native code, .so libraries under lib/<architecture>/. jadx turns the DEX back into readable Java. Obfuscated class and method names (a, b, c) stay that way, but the logic is all there.

JNI and native libraries

A Java method marked native is implemented in C or C++ in a .so loaded with System.loadLibrary. By convention the exported function is named Java_<package>_<class>_<method>, which makes it easy to find in the symbol table. jadx can't see that code; you need a disassembler.

Frida

Frida injects a JavaScript runtime into the app process and lets you replace Java method implementations (Java.use) and intercept native functions (Interceptor.attach) while the app runs. In spawn mode (-f), Frida starts the app with the hooks already in place, before any app code runs.

MASVS-RESILIENCE

MASVS is OWASP's standard of mobile security requirements. The RESILIENCE group is about making reverse engineering harder: RESILIENCE-1 validates the integrity of the platform (root, emulator), RESILIENCE-2 is anti-tampering, RESILIENCE-3 hinders static analysis and RESILIENCE-4 hinders dynamic analysis (debuggers, instrumentation). None of these controls stops an attack; they raise its cost.


Level 1: all Java

onCreate runs three root checks (an su on the PATH, Build.TAGS containing test-keys, and a list of SuperSU files) and one debuggable check. If any of them fires, a dialog appears whose only button calls System.exit(0). The secret is checked in sg.vantagepoint.uncrackable1.a: 

bArrA = sg.vantagepoint.a.a.a(
    b("8d127684cbc37c17616d806cf50473cc"),
    Base64.decode("5UJiFctbmgbDoLXmpL12mkno8HT4Lv8dlat8FxR2GOc=", 0));
return str.equals(new String(bArrA));

sg.vantagepoint.a.a.a decrypts with Cipher.getInstance("AES"), which on Android means AES/ECB/PKCS5Padding. The key and the ciphertext are in the code, so you can decrypt outside the app: 

import base64
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes

key = bytes.fromhex("8d127684cbc37c17616d806cf50473cc")
ct = base64.b64decode("5UJiFctbmgbDoLXmpL12mkno8HT4Lv8dlat8FxR2GOc=")
d = Cipher(algorithms.AES(key), modes.ECB()).decryptor()
print(d.update(ct) + d.finalize())
# b'I want to believe\x0f\x0f...'  (the \x0f bytes are PKCS#7 padding)

The secret is I want to believe.

With Frida

The root checks are in sg.vantagepoint.a.c, and the decryption returns the secret in the clear. Neutralize the first and read the return value of the second: 

// frida -U -f owasp.mstg.uncrackable1 -l level1.js
Java.perform(() => {
  const root = Java.use('sg.vantagepoint.a.c');
  root.a.implementation = () => false;
  root.b.implementation = () => false;
  root.c.implementation = () => false;

  const JString = Java.use('java.lang.String');
  const aes = Java.use('sg.vantagepoint.a.a');
  aes.a.implementation = function (key, data) {
    const out = this.a(key, data);
    console.log('secret: ' + JString.$new(out));
    return out;
  };
});

The decryption hook only fires after you submit some text in the app. Controls: RESILIENCE-1 (root) and, because the key is in the code, MASVS-CRYPTO-2, which covers key management.


Level 2: the secret moves to native code

The Java side keeps the same root checks and adds an AsyncTask that loops until Debug.isDebuggerConnected() is true and then shows the dialog that closes the app. The check is now CodeCheck.bar(byte[]), a native method in libfoo.so, and onCreate first calls a native init().

In the x86_64 build of the library, init calls fork. The child process attaches to the parent with ptrace and waits in waitpid. A process accepts only one tracer at a time, so a debugger can no longer attach to the app. Here is bar in objdump (excerpt): 

112d: cmp    BYTE PTR [rip+0x2ed8],0x1      ; has init() run?
1134: jne    119a                           ; if not, return false
113f: movaps xmm0,XMMWORD PTR [rip+0x7a]    ; 16 constant bytes
1146: movaps XMMWORD PTR [rsp],xmm0
114a: mov    DWORD PTR [rsp+0x10],0x66206568 ; "he f"
1152: mov    WORD PTR [rsp+0x14],0x7369      ; "is"
1159: mov    BYTE PTR [rsp+0x16],0x68        ; "h"
...
1181: cmp    eax,0x17                        ; is the input 23 bytes?
1189: mov    edx,0x17
1191: call   strncmp@plt

The secret is built on the stack: 16 bytes copied from a constant in the binary plus 7 written as little-endian immediates. Put together: Thanks for all the fish, 23 bytes, the length the code requires.

The first comparison matters too. bar only works if a global flag set by init equals 1. Anyone who tries to remove the anti-debugging by deleting the call to init() in smali gets "Nope..." for every input, the right one included.

With Frida

Spawn mode takes care of the anti-debugging: Frida is already inside the process before init creates the child. The secret arrives in the clear as the second argument to libc's strncmp, and filtering on length 23 avoids printing every comparison in the process: 

// frida -U -f owasp.mstg.uncrackable2 -l level2.js
Java.perform(() => {
  const root = Java.use('sg.vantagepoint.a.b');
  root.a.implementation = () => false;
  root.b.implementation = () => false;
  root.c.implementation = () => false;
});

const strncmp = Process.getModuleByName('libc.so')
  .getExportByName('strncmp');
Interceptor.attach(strncmp, {
  onEnter(args) {
    if (args[2].toInt32() === 23) {
      console.log('secret: ' + args[1].readUtf8String(23));
    }
  }
});

You have to type any 23-character string, because with any other length bar returns before reaching strncmp. Controls: RESILIENCE-1 and RESILIENCE-4 (debugger).


Level 3: integrity, anti-Frida and an obfuscated secret

The Java defenses

First, verifyLibs() opens the APK as a zip and compares the CRC32 of each lib/<architecture>/libfoo.so with values stored in the resources, and the CRC32 of classes.dex with the value returned by the native method baz(). Any mismatch sets tampered = 31337, so repackaging the APK with modified smali already trips the detection. Then come the same root checks (now in sg.vantagepoint.util.RootDetection), the debugger loop and a call to init(xorkey), where xorkey is pizzapizzapizzapizzapizz.

The native defenses

The library has a constructor in .init_array that runs as soon as System.loadLibrary loads it, before any native method is called. It starts a thread that reads /proc/self/maps in a loop, with a usleep between reads, looking for the strings frida and xposed with strstr. On a match it logs "Tampering detected! Terminating..." and calls goodbye(), which does raise and _exit. Later, init copies the xorkey into a global and repeats the level 2 fork and ptrace.

The constructor and init each add 1 to a global counter, and bar only accepts input when the counter equals 2. As in level 2, removing one of the defenses from the binary breaks the check with it.

The secret

bar requires a 24-byte input and checks, byte by byte, whether input[i] == xorkey[i] ^ buf[i]. buf is filled by an unnamed function at 0x12c0 in the x86_64 build. It has about 2,300 instructions, makes 100 calls to malloc and uses the constants 0x41c64e6d and 0x3039, the ones from the classic rand() linear congruential generator, to build and walk structures that don't affect the result. Reading it by hand would take hours.

Running it was faster. The function doesn't depend on app state and only calls malloc, so it can run on its own in Unicorn: load the .so segments, apply the relocations (the code reads pointers from the GOT), replace malloc with an allocator that just bumps a pointer, and call the function with an empty buffer: 

BASE, OUT, STOP = 0x10000000, 0x50000000, 0x60000000
MALLOC_PLT = BASE + 0xc70

# ... map the PT_LOAD segments at BASE, apply R_X86_64_RELATIVE and GLOB_DAT,
#     map heap, stack, OUT and STOP

def on_code(uc, addr, size, _):
    if addr == MALLOC_PLT:                       # malloc(n): bump allocator
        n = uc.reg_read(UC_X86_REG_RDI)
        uc.reg_write(UC_X86_REG_RAX, heap.alloc(n))
        ret_to_caller(uc)                        # pop and return

mu.hook_add(UC_HOOK_CODE, on_code)
mu.reg_write(UC_X86_REG_RDI, OUT)                # output buffer
push_return_address(mu, STOP)
mu.emu_start(BASE + 0x12c0, STOP)

buf = bytes(mu.mem_read(OUT, 24))
print(bytes(b ^ k for b, k in zip(buf, b"pizzapizzapizzapizzapizz")))
buf    1d0811130f1749150d0003195a1d1315080e5a0017081314
secret b'making owasp great again'

With the result in hand, I searched for the bytes in the binary. The first 16 sit in a row in .rodata at 0x3b40, right before the string /proc/self/maps. The obfuscation hides how the bytes reach the buffer; the bytes are still in the file.

With Frida

The APK doesn't need to change, so the CRC check isn't in the way. What's left are the root checks, which go away as in the earlier levels, and the thread looking for frida in /proc/self/maps. A hook on libc's strstr that answers "not found" for those two needles disarms the thread without touching the app's library. Because the thread starts when libfoo.so loads, spawn mode is required so the hook is in place before System.loadLibrary: 

// frida -U -f owasp.mstg.uncrackable3 -l level3.js
const strstr = Process.getModuleByName('libc.so')
  .getExportByName('strstr');
Interceptor.attach(strstr, {
  onEnter(args) {
    const needle = args[1].readUtf8String();
    this.hide = needle === 'frida' || needle === 'xposed';
  },
  onLeave(retval) {
    if (this.hide) retval.replace(ptr(0));
  }
});

Java.perform(() => {
  const root = Java.use('sg.vantagepoint.util.RootDetection');
  root.checkRoot1.implementation = () => false;
  root.checkRoot2.implementation = () => false;
  root.checkRoot3.implementation = () => false;
});

With the app open and instrumented, the secret still has to come out of buf, which only exists on the stack while bar runs. For that, the emulation above is still the shortest path. Controls: RESILIENCE-1, RESILIENCE-2 (the APK CRC), RESILIENCE-3 (the obfuscated function) and RESILIENCE-4 (ptrace and Frida detection).


What this means for defenders

Every protection in the three levels runs on the device and ends in a boolean or a call to exit, and whoever controls the device controls both. The Frida detection, for example, looks for a fixed string with a libc function, and one hook on that function is enough to blind it. More serious detections look for several signals at once (ports, threads with known names, pieces of the agent's code in memory), make their calls through direct syscalls and check their own integrity, but they still run on the attacker's ground.

The secret should never be on the client either. In all three levels it is entirely inside the APK, encrypted with a key that is also in the APK or hidden behind obfuscation an emulator walks right through. In a real app, the equivalent is an API key, a signing secret or a business rule that only the client checks.

My takeaway is to treat these protections as friction and telemetry: they slow the attacker down and tell the backend something is wrong, and the decision stays on the server. On Android, that means requesting a Play Integrity verdict and validating it on the backend instead of trusting what the app says about itself.


Final thoughts

Almost all the work in level 3 went into the obfuscated function, and running it in a CPU emulator was far faster than reading it. Obfuscation like this is expensive for someone reading the code and nearly free for someone who can run it. Level 4 (r2pay) and the two license crackmes in the same repository use heavier obfuscation and are left for a future post.
