oraclint and oraclewatch: both sides of a Chainlink oracle

Oct 22, 2026

Smart contracts have no access to data outside the blockchain. To know what an ETH is worth, a lending protocol depends on an oracle, and the most widely used one is Chainlink's Data Feeds network. That puts trust in two places. One is the node operators, who run the infrastructure that signs and publishes prices. The other is the consuming protocols, whose code assumes those prices are correct, recent and within reasonable bounds.

I wrote two open source tools in Go, one for each side. oraclint is a static security linter for Chainlink node configuration that runs before deploy. oraclewatch is a daemon that reads the feeds directly from the chain and alerts when the consumer's assumptions stop holding. Neither is affiliated with Chainlink Labs.

Concepts

Data Feeds and the aggregator contract

A Data Feed is a pair of contracts: a proxy, a fixed address the consumer calls, and an aggregator, which receives the nodes' reports and stores the consolidated value. The consumer reads the price with latestRoundData(), which returns the value (answer), the round ID and the start and update timestamps. A feed updates when the price moves more than a threshold (deviation threshold) or when the heartbeat, the maximum interval between updates, runs out.

Aggregators also have bounds, minAnswer and maxAnswer. Many people assume a report outside that range gets clamped to the bound, but it is rejected, and the feed stays at the last accepted value. That behavior is in the source code of the deployed aggregators and explains one of the incidents described further down.

L2 sequencer

On rollups such as Arbitrum, Base and OP Mainnet, a single sequencer orders transactions. If it goes down, prices stop updating; when it comes back, the queued transactions execute first, possibly against stale prices. That is why Chainlink publishes sequencer uptime feeds, and audits usually require the consumer to check the sequencer and wait out a grace period after recovery.

The Chainlink node

On the operator side, a node is a process that holds keys, signs transactions and reports and exposes an operator interface (port 6688) for managing jobs, keys and bridges. Its configuration lives in a config.toml and a secrets.toml, usually alongside a docker-compose file, Kubernetes manifests and .env files. Many compromised nodes fell to configuration, with no exploit involved: an interface exposed to the internet, a database without TLS, a short keystore password, an RPC key committed to the repository.


oraclint: a configuration linter for nodes

Terraform and Kubernetes have tfsec, checkov and kube-bench, which flag insecure configuration before deploy, with the exact location and a suggested fix. I could not find anything like that for Chainlink nodes, and oraclint fills that role. It reads the node's files and the surrounding infrastructure, runs fully offline and never connects to a running node.

Rules checked against the node's code

There are 35 rules, covering node configuration, secrets, file permissions, docker-compose, Kubernetes and dotenv. I checked each one against the node's source code and documentation at version v2.69.0: key name, default value and actual behavior. When the behavior could not be confirmed, the rule was marked experimental or left out. The README lists the discarded candidates and why, such as database password complexity (the node already refuses weak passwords at startup) and pprof (always behind authentication in the node's router).

Default values

A missing key is evaluated with the node's real default value. With several configuration files, oraclint merges them using the same override semantics the node uses. That avoids both false positives and false negatives, and it is the main reason a generic TOML linter does not work here.

Architecture

oraclint is a linear pipeline of small packages: 

cli → loader → model → engine ← rules (35)
                         │
                         ▼
                 suppress → redact → filter/sort → report (text | JSON | SARIF)

The loader finds the files and classifies them by name and content, and the model keeps each value together with its file:line:column. Each rule is a Go type with two methods and a pure function of the target, in its own file. Before rendering, every message goes through redact. oraclint never prints a secret: there are two layers of redaction, and a fuzz test checks this across all output formats. Hostile input is handled too: YAML alias bombs, deep nesting, binary files and symlinks that point outside the scan root (the walk uses os.Root).


oraclint in practice

You can install it with Go, a release binary or Docker: 

go install github.com/brennocm/oraclint/cmd/oraclint@latest
docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/src:ro" -w /src \
  ghcr.io/brennocm/oraclint:latest scan .

The repository includes a deliberately insecure node in examples/insecure-node. An excerpt of the output:

Rule NS-DKR-001 relates to the problem I described in the article about the Tor bridge: Docker publishes ports by inserting its own firewall rules, so a published port is often reachable even with ufw set to block it. The fix is to publish the operator interface on loopback only and reach it through an SSH tunnel.

Suppressions require a reason

Every suppression, inline or in .oraclint.yaml, needs a reason. A directive without one is ignored and becomes an informational finding. Suppressed findings stay in the JSON and SARIF output, with the reason recorded: 

[WebServer.TLS]
# oraclint:ignore NS-WEB-001 reason="TLS is terminated at the load balancer"
HTTPSPort = 0

When scanning untrusted content, such as pull requests from forks, use --ignore-suppressions to apply only your own policy, because the PR itself could bring an .oraclint.yaml that silences everything.

CI integration

The repository also works as a GitHub Action. With SARIF 2.1.0 output, findings show up in GitHub's code scanning tab: 

jobs:
  scan:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      security-events: write
    steps:
      - uses: actions/checkout@v7
      - uses: brennocm/oraclint@v0.1.0   # pin to a commit SHA in production
        with:
          path: .
          format: sarif
          output: oraclint.sarif
          fail-on: high
      - uses: github/codeql-action/upload-sarif@v4
        if: always()
        with:
          sarif_file: oraclint.sarif

Exit codes follow the linter convention: 0 with no findings above the threshold, 1 with findings and 2 for a usage error. A file that cannot be parsed produces a high-severity parse-error finding, so a broken file fails the build. On the example deployment (5 files, 35 rules), a full scan takes about 4 ms.


oraclewatch: consumer-side monitoring

Chainlink operates and monitors its Data Feeds, but the risk of using a feed belongs to the protocol that consumes it. oraclewatch continuously runs the checks auditors ask for on-chain (recent updatedAt, answer > 0, sequencer up and grace period), plus a few that only make sense off-chain, and pages a person when something looks wrong. The catalog came out of three real incidents:

  1. LUNA/USD, May 2022. The market price fell below the aggregator's minAnswer. Since out-of-range reports are rejected, the feed stuck at about US$ 0.107 while LUNA traded at US$ 0.01. Attackers bought at market, deposited it as collateral at the oracle price and borrowed against it. Venus and Blizz Finance lost about US$ 11M and US$ 8.3M. The checks FW-DEV-001 (~970% deviation), FW-STALE-001 and FW-CB-001 flag this condition.
  2. Moonwell wrsETH, November 2025. An exchange-rate feed reported 1 wrsETH = 1.65 million ETH, and the attack took 30 seconds. FW-JUMP-001 flags the jump, but in 30 seconds an alert does not arrive in time, which is why the monitor does not replace on-chain sanity bounds.
  3. Arbitrum sequencer outage, December 2023. About 78 minutes of downtime, covered by FW-SEQ-001, FW-SEQ-002 and FW-CHAIN-001.

The check catalog

There are 16 checks with stable IDs, each documented with its exact logic, default parameters and known false positives. By group:

  1. Feed health: a feed stuck past its heartbeat (FW-STALE-001), invalid round data (FW-INVALID-001), closeness to the circuit breaker bounds (FW-CB-001) and implausible jumps between rounds (FW-JUMP-001, experimental).
  2. Market: deviation from the median of several exchanges (FW-DEV-001), with an explicit "reference untrusted" state when too few exchanges respond or they disagree (FW-REF-001), and divergence of the same pair across networks (FW-XCHAIN-001).
  3. Contract changes: the proxy pointing to a new aggregator (FW-AGG-001) and mismatched decimals or description (FW-META-001).
  4. Source trust: RPCs returning different data for the same block (FW-RPC-001), fork views (FW-RPC-002), wrong chain ID (FW-RPC-003) and a stalled head (FW-CHAIN-001).
  5. L2: sequencer down (FW-SEQ-001) and still inside the grace period (FW-SEQ-002).
  6. The monitor itself: FW-SELF-001 fires when there are no successful reads for N cycles. In that case oraclewatch reports that it has no data instead of guessing the state of the feeds.

One pinned block per cycle

Every value a check compares comes from the same block. There is one goroutine per network, and each cycle starts by pinning a block: min(head) - confirmations across all available endpoints. Endpoints with a lagging head are excluded, the block hash is compared across the rest (majority wins) and then every feed is read from every endpoint at that block.

That is what lets FW-RPC-001 treat any difference as critical: two honest RPCs queried at the same block must return identical bytes. It also makes staleness use the chain's own clock instead of the clock of the machine running the monitor.

Checks are pure functions, with no I/O and no clock, using exact arithmetic in math/big. Their results feed an alert state machine (OK → PENDING → FIRING → RESOLVING) with for:, hysteresis, cooldown and grouping when many alerts fire at once. Alerts go to Discord, Telegram or stdout, and there are Prometheus metrics and a Grafana dashboard.


oraclewatch in practice

check mode runs a single cycle across all networks and exits with 0 (ok), 1 (some result at or above --fail-on) or 2 (error), which works for CI or cron. RPC URLs are written as ${VAR} and expanded from the environment, only in secret fields: 

cp .env.example .env     # two RPCs from different providers per network, notifiers
make build && set -a && . ./.env && set +a
./bin/oraclewatch check --config configs/example.yaml

A real run against ETH/USD on Ethereum and Arbitrum, using public RPCs (trimmed output):

In FW-STALE-001, the Ethereum feed was updated 53 minutes ago and is still healthy, because the ETH/USD heartbeat on mainnet is one hour. That is why each feed carries its own parameters, copied from the official files, instead of a global limit.

To run the daemon with Prometheus, Grafana and TLS, there is a ready-made compose file, and the documentation walks through a deployment on an arm64 Oracle Cloud Always Free instance, the same base I used for OCI-SecOps: 

docker compose -f deploy/docker-compose.yml --env-file .env up -d

The example configuration monitors ETH/USD, BTC/USD and USDC/USD on Ethereum, Arbitrum, Base and OP Mainnet, plus the sequencer uptime feeds for the three L2s. No address was typed by hand. All of them came from the data files behind the official page and were checked on-chain against two RPCs at the same block, and a test keeps the example identical to the verified lists.


Securing the tools themselves

Both tools run close to sensitive infrastructure, so I also tried to make them hard to attack:

  1. Small surface. oraclint does not touch the network and has three direct runtime dependencies (cobra, go-toml, yaml). oraclewatch uses only eth_chainId, eth_getBlockByNumber and eth_call; the program holds no private key, and a test fails if the binary links any key management or transaction signing package.
  2. Secrets do not leave the process. Strings, errors (including *url.Error, which tends to leak the full RPC URL with its API key) and logs are redacted, and end-to-end tests check it.
  3. On the supply chain side, Actions are pinned by SHA, Dependabot is on and releases go through GoReleaser with checksums signed via cosign (keyless, Sigstore), an SPDX SBOM and SLSA provenance you can check with gh attestation verify.
  4. Each repository has a THREAT_MODEL.md, and design decisions are recorded in ADRs.

Limitations

oraclint is static analysis: it sees files, not the running node, and the rules were written for v2.69.0, so they may be wrong for other versions. Helm charts must be rendered with helm template first.

oraclewatch takes the polling interval (60 s by default) plus confirmations to detect a problem. An attacker watching the same feed acts within a block, and the monitor alerts people without stopping any transaction. It does not replace on-chain validation in the consuming contract, which is still the first line of defense, and it does not cover prices the protocol derives by combining several feeds.


Final thoughts

oraclint runs before deploy and turns node operation best practices into rules CI can check. oraclewatch runs afterwards, checking all the time whether the consumer's assumptions still hold.

In both projects I tried not to rely on any assumption I had not checked. Every oraclint rule was checked against the node's code, every oraclewatch check has a real incident or documented research behind it, and both say when they do not know the answer (parse-error, FW-SELF-001) instead of passing silently.
