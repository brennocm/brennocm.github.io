OWASP UnCrackable: engenharia reversa dos níveis 1 a 3 no Android

24 nov 2026

Os UnCrackable são os crackmes oficiais do OWASP MASTG, o guia de testes de segurança de apps mobile. Cada app pede um segredo e mostra "Success!" quando ele está certo, e a cada nível aparece uma proteção nova: detecção de root em Java no primeiro, a verificação movida para código nativo com anti-debug no segundo, e checagem de integridade, detecção de Frida e um segredo gerado por código ofuscado no terceiro.

Resolvi os três por análise estática: jadx para o bytecode, objdump para as bibliotecas nativas e, no nível 3, o Unicorn para executar só a função que monta o segredo, sem rodar o app. Para cada nível também deixo o caminho dinâmico com Frida, para quem tem um emulador com root, e o controle do MASVS que a proteção tenta atender. No fim, o que isso diz para quem escreve as defesas.

Os APKs são os do repositório do MASTG. Para conferir que é a mesma versão:

Conceitos

APK, DEX e jadx

Um APK é um zip com o manifesto, os recursos, o bytecode do app (classes.dex) e, quando há código nativo, bibliotecas .so em lib/<arquitetura>/. O jadx transforma o DEX de volta em Java legível. Nomes de classes e métodos ofuscados (a, b, c) continuam assim, mas a lógica aparece inteira.

JNI e bibliotecas nativas

Um método Java marcado como native é implementado em C ou C++ numa .so, carregada com System.loadLibrary. Por convenção, a função exportada se chama Java_<pacote>_<classe>_<método>, e por isso fica fácil achá-la na tabela de símbolos. O jadx não vê esse código; para ele é preciso um disassembler.

Frida

O Frida injeta um runtime JavaScript no processo do app e permite trocar a implementação de métodos Java (Java.use) e interceptar funções nativas (Interceptor.attach) com o app rodando. No modo spawn (-f), o Frida inicia o app já com os hooks, antes de qualquer código do app rodar.

MASVS-RESILIENCE

O MASVS é o padrão de requisitos de segurança mobile do OWASP. O grupo RESILIENCE trata de dificultar a engenharia reversa: RESILIENCE-1 valida a integridade da plataforma (root, emulador), RESILIENCE-2 é anti-tampering, RESILIENCE-3 dificulta a análise estática e RESILIENCE-4 dificulta a análise dinâmica (debugger, instrumentação). Nenhum desses controles impede um ataque; eles aumentam o custo.


Nível 1: tudo em Java

O onCreate roda três checagens de root (um su no PATH, Build.TAGS com test-keys e uma lista de arquivos do SuperSU) e uma de app debuggable. Se qualquer uma dá positivo, aparece um diálogo cujo único botão chama System.exit(0). O segredo é conferido em sg.vantagepoint.uncrackable1.a: 

bArrA = sg.vantagepoint.a.a.a(
    b("8d127684cbc37c17616d806cf50473cc"),
    Base64.decode("5UJiFctbmgbDoLXmpL12mkno8HT4Lv8dlat8FxR2GOc=", 0));
return str.equals(new String(bArrA));

A função sg.vantagepoint.a.a.a decifra com Cipher.getInstance("AES"), que no Android significa AES/ECB/PKCS5Padding. A chave e o texto cifrado estão no próprio código, então dá para decifrar fora do app: 

import base64
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes

key = bytes.fromhex("8d127684cbc37c17616d806cf50473cc")
ct = base64.b64decode("5UJiFctbmgbDoLXmpL12mkno8HT4Lv8dlat8FxR2GOc=")
d = Cipher(algorithms.AES(key), modes.ECB()).decryptor()
print(d.update(ct) + d.finalize())
# b'I want to believe\x0f\x0f...'  (os \x0f são o padding PKCS#7)

O segredo é I want to believe.

Com Frida

As checagens de root estão em sg.vantagepoint.a.c, e a decifração devolve o segredo em claro. Basta neutralizar uma e ler o retorno da outra: 

// frida -U -f owasp.mstg.uncrackable1 -l level1.js
Java.perform(() => {
  const root = Java.use('sg.vantagepoint.a.c');
  root.a.implementation = () => false;
  root.b.implementation = () => false;
  root.c.implementation = () => false;

  const JString = Java.use('java.lang.String');
  const aes = Java.use('sg.vantagepoint.a.a');
  aes.a.implementation = function (key, data) {
    const out = this.a(key, data);
    console.log('segredo: ' + JString.$new(out));
    return out;
  };
});

O hook da decifração só dispara depois que algum texto é enviado no app. Controles: RESILIENCE-1 (root) e, pela chave no código, MASVS-CRYPTO-2, que trata de gestão de chaves.


Nível 2: o segredo vai para o código nativo

O Java continua com as mesmas checagens de root e ganha uma AsyncTask que fica em loop até Debug.isDebuggerConnected() ser verdadeiro e então mostra o diálogo que fecha o app. A verificação agora é CodeCheck.bar(byte[]), um método nativo em libfoo.so, e o onCreate chama antes um init() nativo.

Na versão x86_64 da biblioteca, o init chama fork. O processo filho se anexa ao pai com ptrace e fica esperando com waitpid. Um processo só aceita um tracer por vez, então um debugger não consegue mais se anexar ao app. O bar fica assim no objdump (trecho): 

112d: cmp    BYTE PTR [rip+0x2ed8],0x1      ; init() já rodou?
1134: jne    119a                           ; se não, retorna false
113f: movaps xmm0,XMMWORD PTR [rip+0x7a]    ; 16 bytes constantes
1146: movaps XMMWORD PTR [rsp],xmm0
114a: mov    DWORD PTR [rsp+0x10],0x66206568 ; "he f"
1152: mov    WORD PTR [rsp+0x14],0x7369      ; "is"
1159: mov    BYTE PTR [rsp+0x16],0x68        ; "h"
...
1181: cmp    eax,0x17                        ; a entrada tem 23 bytes?
1189: mov    edx,0x17
1191: call   strncmp@plt

O segredo é montado na pilha: 16 bytes copiados de uma constante do binário e mais 7 gravados como imediatos, em little-endian. Juntando os pedaços: Thanks for all the fish, com 23 bytes, o mesmo tamanho que o código exige.

A primeira comparação também importa. O bar só funciona se uma flag global, ligada pelo init, valer 1. Quem tentar remover o anti-debug apagando a chamada a init() no smali recebe "Nope..." para qualquer entrada, inclusive a certa.

Com Frida

O modo spawn resolve o anti-debug: o Frida já está dentro do processo antes do init criar o filho. O segredo chega em claro como segundo argumento do strncmp da libc, e o filtro pelo tamanho 23 evita imprimir todas as comparações do processo: 

// frida -U -f owasp.mstg.uncrackable2 -l level2.js
Java.perform(() => {
  const root = Java.use('sg.vantagepoint.a.b');
  root.a.implementation = () => false;
  root.b.implementation = () => false;
  root.c.implementation = () => false;
});

const strncmp = Process.getModuleByName('libc.so')
  .getExportByName('strncmp');
Interceptor.attach(strncmp, {
  onEnter(args) {
    if (args[2].toInt32() === 23) {
      console.log('segredo: ' + args[1].readUtf8String(23));
    }
  }
});

É preciso digitar qualquer texto de 23 caracteres, porque com outro tamanho o bar retorna antes do strncmp. Controles: RESILIENCE-1 e RESILIENCE-4 (debugger).


Nível 3: integridade, anti-Frida e um segredo ofuscado

As defesas em Java

Antes de tudo, verifyLibs() abre o próprio APK como zip, compara o CRC32 de cada lib/<arquitetura>/libfoo.so com valores guardados nos recursos e o CRC32 do classes.dex com o valor devolvido pelo método nativo baz(). Qualquer diferença marca tampered = 31337. Repacotar o APK com um smali alterado, portanto, já dispara a detecção. Depois vêm as mesmas checagens de root (agora em sg.vantagepoint.util.RootDetection), o loop de debugger e uma chamada a init(xorkey), onde xorkey é pizzapizzapizzapizzapizz.

As defesas nativas

A biblioteca tem um construtor em .init_array, que roda assim que o System.loadLibrary a carrega, antes de qualquer método nativo ser chamado. Ele cria uma thread que lê /proc/self/maps em loop, com um usleep entre as leituras, procurando as strings frida e xposed com strstr. Se encontrar, registra "Tampering detected! Terminating..." e chama goodbye(), que faz raise e _exit. Depois, o init copia a xorkey para uma variável global e repete o fork com ptrace do nível 2.

O construtor e o init somam 1 cada a um contador global, e o bar só aceita a entrada se esse contador valer 2. Como no nível 2, remover uma das defesas no binário quebra a verificação junto.

O segredo

O bar exige uma entrada de 24 bytes e confere, byte a byte, se entrada[i] == xorkey[i] ^ buf[i]. O buf é preenchido por uma função sem nome, no endereço 0x12c0 da versão x86_64. Ela tem cerca de 2.300 instruções, faz 100 chamadas a malloc e usa as constantes 0x41c64e6d e 0x3039, as do gerador congruencial linear clássico do rand(), para montar e percorrer estruturas que não influenciam o resultado. Ler isso à mão levaria horas.

Executar a função foi mais rápido. Ela não depende do estado do app e só chama malloc, então dá para rodá-la isolada no Unicorn: carregar os segmentos da .so, aplicar as relocações (o código lê ponteiros da GOT), trocar o malloc por um alocador que só avança um ponteiro e chamar a função com um buffer vazio: 

BASE, OUT, STOP = 0x10000000, 0x50000000, 0x60000000
MALLOC_PLT = BASE + 0xc70

# ... mapeia os PT_LOAD em BASE, aplica R_X86_64_RELATIVE e GLOB_DAT,
#     mapeia heap, pilha, OUT e STOP

def on_code(uc, addr, size, _):
    if addr == MALLOC_PLT:                       # malloc(n): alocador linear
        n = uc.reg_read(UC_X86_REG_RDI)
        uc.reg_write(UC_X86_REG_RAX, heap.alloc(n))
        ret_to_caller(uc)                        # desempilha e volta

mu.hook_add(UC_HOOK_CODE, on_code)
mu.reg_write(UC_X86_REG_RDI, OUT)                # buffer de saída
push_return_address(mu, STOP)
mu.emu_start(BASE + 0x12c0, STOP)

buf = bytes(mu.mem_read(OUT, 24))
print(bytes(b ^ k for b, k in zip(buf, b"pizzapizzapizzapizzapizz")))
buf     1d0811130f1749150d0003195a1d1315080e5a0017081314
segredo b'making owasp great again'

Depois de ter o resultado, procurei os bytes no binário. Os 16 primeiros estão em sequência na .rodata, no endereço 0x3b40, logo antes da string /proc/self/maps. A ofuscação esconde como os bytes chegam ao buffer; os bytes continuam no arquivo.

Com Frida

O APK não precisa ser alterado, então a checagem de CRC não atrapalha. Sobram as checagens de root, que saem como nos níveis anteriores, e a thread que procura frida no /proc/self/maps. Um hook no strstr da libc que responde "não encontrado" para essas duas agulhas desarma a thread sem tocar na biblioteca do app. Como a thread nasce no carregamento da libfoo.so, o modo spawn é obrigatório, para o hook já estar lá antes do System.loadLibrary: 

// frida -U -f owasp.mstg.uncrackable3 -l level3.js
const strstr = Process.getModuleByName('libc.so')
  .getExportByName('strstr');
Interceptor.attach(strstr, {
  onEnter(args) {
    const needle = args[1].readUtf8String();
    this.hide = needle === 'frida' || needle === 'xposed';
  },
  onLeave(retval) {
    if (this.hide) retval.replace(ptr(0));
  }
});

Java.perform(() => {
  const root = Java.use('sg.vantagepoint.util.RootDetection');
  root.checkRoot1.implementation = () => false;
  root.checkRoot2.implementation = () => false;
  root.checkRoot3.implementation = () => false;
});

Com o app aberto e instrumentado, o segredo ainda precisa sair do buf, que só existe na pilha durante o bar. Para isso, o caminho mais curto continua sendo a emulação acima. Controles: RESILIENCE-1, RESILIENCE-2 (CRC do APK), RESILIENCE-3 (a função ofuscada) e RESILIENCE-4 (ptrace e detecção de Frida).


O que isso diz para quem defende

Todas as proteções dos três níveis rodam no aparelho e terminam num booleano ou numa chamada a exit, e quem controla o aparelho controla os dois. A detecção de Frida, por exemplo, procura uma string fixa com uma função da libc, e um hook nessa função basta para cegá-la. Detecções mais sérias procuram vários sinais ao mesmo tempo (portas, threads com nomes conhecidos, trechos de código do agente na memória), fazem as chamadas por syscall direta e checam a própria integridade, mas continuam rodando no território de quem ataca.

O segredo também nunca deveria estar no cliente. Nos três níveis, ele está inteiro no APK, cifrado com uma chave que está no APK ou escondido atrás de ofuscação que um emulador atravessa. Num app real, o equivalente é uma chave de API, um segredo de assinatura ou uma regra de negócio que só o cliente checa.

Para mim, a conclusão é usar essas proteções como atrito e como telemetria: elas atrasam quem ataca e avisam o backend que algo está errado, e a decisão fica no servidor. No Android, isso significa pedir um veredito do Play Integrity e validá-lo no backend, em vez de confiar no que o app diz sobre si mesmo.


Considerações finais

Quase todo o trabalho do nível 3 ficou na função ofuscada, e executá-la num emulador de CPU foi bem mais rápido que lê-la. Ofuscação desse tipo custa caro para quem lê o código e quase nada para quem pode rodá-lo. O nível 4 (r2pay) e os dois crackmes de licença do mesmo repositório usam ofuscação mais pesada e ficam para um próximo post.
